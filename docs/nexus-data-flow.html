1. Session Start -- Three Trigger Paths

Sessions enter the system through three distinct paths. Ad-hoc sessions originate from Claude Code lifecycle hooks writing event files and socket messages. Managed sessions are spawned by the TUI or Dashboard via gRPC, which creates a tmux window running Claude. HTTP-triggered sessions follow a similar pattern through the REST API. All three paths converge on the SessionRegistry for deduplication and persistence.

2. Session Registration and Storage

The SessionRegistry maintains an in-memory HashMap guarded by a RwLock, backed by SQLite for durability. Every session state change is persisted to the sessions table with full metadata. On daemon restart, load_active_sessions() recovers any sessions that were still running (ended_at IS NULL), ensuring no session is lost across agent restarts.

3. Session Interaction

Users interact with sessions through two primary interfaces: the TUI for terminal-based read-only streaming via WebSocket, and the Next.js Dashboard for visual monitoring with live terminal panels. The StreamManager fans out PTY output to all connected clients and maintains a 10K-line ring buffer for reconnection replay. The HTTP API supports filtering by project and status with a 1-second TTL cache.

4. Dead Session Detection

Dead session detection operates through a multi-layered approach. The Rust registry checks for stale sessions based on heartbeat age and idle thresholds, while the Node session-manager runs a 60-second sweep cycle with three passes: marking active sessions as idle, promoting idle to errored or stale, and evicting ended sessions past their TTL. The /proc filesystem serves as the ground truth for process liveness.

5. Session Kill

Session termination follows a graceful-then-forceful pattern. The system sends SIGTERM first, then polls every 250ms for up to 10 seconds. If the process survives, SIGKILL is sent with a tighter 50ms polling loop. The unregister path handles the clean case where Claude Code exits normally and its postExitHook notifies the registry without needing a kill signal.

6. Credential Storage and Monitoring

The credential system manages multiple Anthropic OAuth accounts through a CredentialPool backed by filesystem storage and SQLite polling history. On startup, it scans the credential directory and bootstraps utilization data from the database or a disk-based JSON cache. A 300-second polling loop queries the Anthropic usage API for each account, recording five-hour and seven-day utilization windows. File watchers on both the credential directory and the Claude config directory detect account changes in real time.

7. Credential Switching / Swap

Credential swapping selects the least-utilized account through a filtering and scoring pipeline: expired and maxed-out accounts are excluded, and the remaining accounts are ranked by their effective utilization (the maximum of five-hour and seven-day rates). The swap itself is atomic -- a temporary symlink is created in /tmp and then renamed over the target path in a single rename(2) syscall. A 180-second debounce prevents thrashing. The TypeScript pool uses a Postgres-backed lease system with weighted round-robin for the Bun agent layer.

8. Credential Surfacing and Health

Credential data is surfaced through secured HTTP endpoints that expose utilization metrics without ever returning tokens or file paths. The Rust agent on port 7402 and the Bun agent both require the X-Nexus-Secret header for authentication. A dedicated health-check endpoint probes the Anthropic API with the decrypted token to verify account validity, emitting an audit log entry for every check regardless of outcome.
