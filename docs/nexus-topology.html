00 · overview

A mesh of daemons,
no king in the middle.

Two machines, two daemons. homelab runs the long-lived sessions and the Postgres of record; macbook runs the developer's TUI and the audio stack. They discover each other through agents.toml and federate over a single WebSocket. There is no hub, no broker, no proxy.

Plate 00 · TOPOLOGY.MESH view · tailscale + loopback
Note · 00.1
Agents bind to both loopback and the Tailscale interface IP. The effect: an agent is reachable from itself and from any other Tailnet peer, and from nowhere else. No tokens, no JWT, no API key — the network is the auth. See apps/agent/src/server.ts:149-171.
01 · session registration

Two ingress paths.
One Map behind them.

Sessions enter through one of three doors. Two are real ingress paths for session events: HTTP POST /hooks and AF_UNIX agent.sock. One is a reconciliation sweep that finds CC processes that never installed hooks. The third (lifecycle bus) isn't really a drain — it's fan-out. All paths converge on the same write-through cache and produce byte-identical envelopes downstream.

Plate 01a · MANAGED · ingress POST /hooks + AF_UNIX · both feed dispatcher
Plate 01b · UNMANAGED / UNHOOKED pgrep reconcile · the discovery fallback
Plate 01c · CONVERGENCE + TIMING session-manager.ts · the Map cache · envelope contract
Note · 01.1
The cache is always a subset of the DB, never a divergent truth — write-through pattern at session-manager.ts:288. The bigger question (raised by you and addressed in §08) is whether the bus emit should await the DB write before fanning out. The current emit-then-persist racey shape works only because envelopes carry the full payload — remove that and the race becomes real.
Note · 01.2
On the "three drains" framing: there are really two ingress paths (HTTP /hooks + AF_UNIX) feeding one dispatcher, then one fan-out bus distributing to consumers. The dispatcher is the single source of normalisation; the bus is the single source of distribution. The two ingress paths exist for one good reason — HTTP works across machines (Tailscale), the socket doesn't — and that asymmetry justifies keeping both. See §08 for the collapse analysis.

Seven mouths,
one bus.

Seven distinct sources push signal into the agent. Each has its own trigger, its own cadence, and its own schema — but every one of them ends up as an envelope on the same lifecycle bus. Read each plate as a stand-alone subsystem.

03 · the pipeline

Cached · recorded
· transmitted · emitted

Telemetry takes one of four exits. Hot state lives in-memory and is cheap to query. Durable state lands in Postgres. Live updates fan out over SSE and WebSocket. Side-effects (audio, banners, slack) emerge at the edges of the graph.

03.1 · CACHED (volatile, in-process)

What lives in RAM and dies with the process

Four caches sit inside the agent process. Each one trades durability for latency — a query that hits the cache returns in microseconds, a query that misses falls through to Postgres in milliseconds. Where: nexus-agent heap. When written: on every relevant envelope. How read: synchronous in-process lookup. Why volatile: a restart always reseeds from Postgres via readThroughAsync().

Session Map
Map<sessionId, Session> mutated on every WatcherEvent. Sweep runs every 60s and walks the map: active rows older than the heartbeat threshold flip to idle, then stale, then evict. Sweep thresholds now align with CC's 60-minute session cache — the old 5-minute idle was an artefact of an earlier CC build.
Health snapshot
A single latest-only object held in the collector. Refreshed every 5s by systeminformation; the scheduler persists every 6th tick (30s). Docker probe failures back off exponentially 30s → 600s to keep docker-less hosts quiet.
Spec state
One entry per registered project keyed by absolute path. Stores the last-seen content hash and checkbox tally. Mutations come from either the 60s poll or the fs.watch debounce (300ms). The diff is what produces a SpecTransition.
Throttle buffer
A per-key sliding window of 500ms keyed on (eventType, sessionId). tool_use_start and tool_use_end coalesce; all other event types pass through unbuffered. The flush emits one envelope with a count field for the suppressed siblings.
03.2 · RECORDED (durable, postgres)

What survives a restart, a crash, a redeploy

Four tables form the durable record. Where: Postgres on homelab. When written: write-through from the cache on every state mutation; full payload preserved as JSON for replay. How read: Drizzle queries from HTTP routes, never directly from clients. Why durable: the cache is volatile so the DB is the only source of truth across restarts and across peers.

sessions
One row per Claude Code session ever observed. Foreign keys to projects and agents. credentialFingerprint binds every cost-bearing event to the API key that paid for it. Indexed on (machine, status) for the TUI's "show me everything active" query.
session_events
Append-only audit trail. The full hook payload lands in metadata as JSON.stringify — nothing is dropped. This is the source of truth for any replay; if the bus loses an event the row is still here. Read pattern: tail-by-sessionId for the TUI detail view.
health_snapshots
Periodic rollup, one row every 30s per agent. rawJson column carries the entire collector output so ad-hoc analysis doesn't need a schema migration. Default retention 24h, pruned by the nightly cleanup job.
notifications
One row per dispatch. The caller's id doubles as the idempotency key — sending the same notification twice within the dedupe window updates the existing row instead of inserting. Status tracks the full lifecycle: queued → sent → acknowledged | failed.
03.3 · TRANSMITTED (live, streaming)

What goes out on the wire while clients are watching

Four live streams leave the agent. Where: bound to the agent's HTTP server on 7400. When: push-only; each envelope is sent the moment the bus emits. How: long-lived HTTP/1.1 connections (SSE) or WebSocket upgrades. Why streaming: the alternative — clients polling — would either be slow or expensive. SSE is cheaper than WebSocket for one-way push; WebSocket is mandatory for the bidirectional cases.

GET /events/stream · SSE
Server-Sent Events. Subscribes to the lifecycle bus with a wildcard listener; every envelope becomes a data: frame. 30-second comment keepalives so reverse proxies don't drop the connection. The mac notifier is the primary consumer.
/ws/federation · WS bidi
Peer-to-peer WebSocket. Forwards every source: 'local' envelope; ingests peer envelopes tagged source: 'peer' — the source tag is the entire echo-suppression protocol. Per-peer buffer of 1000 events absorbs short disconnects.
/sessions/$id/stream · WS read
Tail-only PTY bytes from the underlying tmux pane. Many viewers can stream the same session in parallel. The StreamManager multiplexes a single PTY source across all subscribers; closing a subscriber leaves the source alive.
/sessions/$id/interact · WS bidi
Full duplex over WebSocket. stdin from the client pumps into the PTY; stdout streams back. Only one driver at a time — the manager rejects a second interact connection while one is held. Loopback/Tailscale-bound only.
03.4 · EMITTED (side-effects at the edges)

What leaves the system entirely

The terminal side-effects: audio, banners, webhooks, peer forwards. Where: the edge of the graph — CoreAudio, Notification Center, Slack, peer machines. When: after a NotificationFired event is dispatched, or after a peer announces interest. How: via OS-native APIs (afplay, terminal-notifier, osascript), HTTP POST (Slack), or WebSocket forward (peers). Why these are the exits: everything before this point lives inside the Nexus boundary; everything here crosses out.

Audio bytes
Base64 mp3 from ElevenLabs synthesized by the agent, decoded by the listener to /tmp/nexus-notifier-$uuid.mp3, played by afplay with a 60s timeout. Volume ducking is applied via osascript before playback and restored after.
Desktop banner
terminal-notifier on macOS — title + body + project tag. Banner click writes the active utterance PID to current-utterance.pid which the player polls each cycle to short-circuit playback.
Slack webhook
HTTP POST to a configured incoming-webhook URL. The shared secret lives in the credential pool, decrypted at send time. Per-channel acknowledgement is tracked in the notifications table.
Peer fan-out
Every source: 'local' envelope is mirrored to every connected peer over /ws/federation. The 1000-event ring buffer protects against short network drops; longer disconnects rely on the DB as the ultimate replay source.
Note · 03.1
Hooks are fire-and-forget by contract (routes/hooks.ts:327-335). Whatever happens downstream — DB write failure, bus saturation, peer unreachable — the HTTP response is always 200. CC must never block on a broken agent.

08 · tradeoffs

Seven proposals,
scored.

The questions you raised in the last review aren't cosmetic. Each one is a real architectural fork. This chapter scores the seven proposed changes against today's shape — what gets better, what gets worse, and whether the trade is worth taking.

08.1 · collapse HTTP /hooks + AF_UNIX into one drain

Do we really need two ingress paths?

Today both POST /hooks and ~/.nexus/agent.sock flow into the same dispatcher. The HTTP path exists so a CC session on a peer machine can reach a local agent. The socket exists for same-machine latency and kernel-level uid auth. Could one handle both?

OptionProsCons
Keep both (today)
KEEP		 HTTP works across the Tailnet for remote CC; socket is ~50× faster for local; either can fail and the other still works; debugging via curl is trivial. Two code paths to throttle, validate, and instrument. Slight risk of divergence if either evolves independently.
HTTP-only
SKIP		 One code path. One throttle. One auth model. Adds ~5-10ms per local hook event. CC's hook scripts must shell out to curl instead of writing a socket — thousands of forks per session.
Socket-only
SKIP		 Lowest latency. Kernel uid auth is free. Peer CC sessions become invisible — no Tailnet-reachable socket. Would need a per-peer SSH tunnel just to deliver events. Federation has to carry hook payloads, which is a different contract from envelope fan-out.
verdict
Keep both. The asymmetry is justified: HTTP is the only Tailnet-reachable ingress, the socket is the only local-fast ingress, and they share 100% of the dispatcher code after the first parse. The "three drains" framing was actually a misread — the lifecycle bus is fan-out, not ingress.
08.2 · wed managed + unmanaged via global hooks

Should every CC session emit hooks, eliminating pgrep as a discovery primitive?

Today, "managed" means hooks installed + tmux session. "Unmanaged" means pgrep discovery + no attach. If hooks were globally installed in ~/.claude/settings.json, every CC session would emit telemetry — the managed/unmanaged distinction would collapse to just the tmux attach axis.

OptionProsCons
Global hooks + keep pgrep
DO		 Every session emits full telemetry. pgrep becomes a corroboration check (catches the rare hook-script-broke case). TUI shows the same fidelity for every card. Sub-agent telemetry available for every session. Requires installing hooks in user's global CC config — one-time bootstrap step. If a user runs CC with --no-hooks we still need pgrep.
pgrep-only (drop hooks)
SKIP		 Zero CC-side dependency. Lose cost, model, ccSessionId, tool telemetry, sub-agent tree, crash signal, monitor channel. The TUI becomes a process viewer instead of a session viewer.
Hooks-only (drop pgrep)
MAYBE		 One discovery path. No /proc parsing. No reconcile loop. Cleaner code. A CC session whose hooks break is now invisible. The reconcile loop is also how we detect dead PIDs — without it, a crashed CC leaves an "active" row forever.
verdict
Install hooks globally, keep pgrep as the safety net. The framing changes from "two ingestion strategies" to "one telemetry path with a liveness watchdog". The tmux/no-tmux distinction stays as the only remaining axis — and it's about attach, not telemetry.
08.3 · raise idle threshold 5m → 60m

Align our sweep with CC's new session cache TTL.

The 5-minute idle threshold was tied to the legacy CC session cache. A recent CC update extended that TTL to 60 minutes; our sweep still flips sessions to idle after 5. The result is noisy "idle" events every coffee break that don't actually reflect a stalled session.

OptionProsCons
Raise to 60m
DO		 Aligns with CC reality. Eliminates false idle transitions. Reduces SSE noise. TUI "idle" badge becomes meaningful. An actual abandoned session takes longer to mark stale — but that's exactly what we want, because CC's own cache treats it as still alive.
Make it configurable
MAYBE		 Per-deployment tuning. CC updates won't bit-rot us again. One more config knob. The right value almost always matches CC's; locking to that is simpler.
verdict
One-line change in session-manager.ts: IDLE_THRESHOLD_MS = 60 * 60 * 1000. The stale + evict thresholds shift proportionally. Update the sidebar diagram and Plate 01c to reflect the new value.
08.4 · sequential persist-then-emit

Should the bus emit only after the DB write commits?

Today both fire async, neither awaits the other. A subscriber that receives an envelope and immediately queries the DB can see a stale row. The current shape is safe only because envelopes carry the full payload — if a future consumer reads-through to the DB on receipt, the race becomes real.

OptionProsCons
Keep concurrent (today)
MAYBE		 Lowest perceived latency on the bus. Subscribers don't wait on DB. Implicit contract: subscribers must never read-through. Hard to enforce. One careless TUI dev introduces a race nobody can reproduce.
Persist-then-emit (proposed)
DO		 Eliminates the race entirely. Subscribers can safely read-through. Easier to reason about — the bus envelope is a "this is true now" notification. Adds DB-roundtrip latency to bus emits — ~5-20ms on healthy Postgres. SSE delivery to mac listener slows by the same amount.
Persist-then-emit + retain payload
DO		 Best of both. Race is gone and subscribers still don't have to read-through because the payload is already enough. Same latency penalty as above. No additional cost.
verdict
Make it sequential. The latency cost is below the human-perceptible threshold for everything we use the bus for (TTS, banners, TUI refresh). The race elimination removes an entire class of "looks intermittent" bugs.
08.5 · surface sub-agent distinction explicitly

The fields already exist — the UI doesn't read them.

Hook payloads already carry agent_type, agent_name, parent_agent, and child_role for every agent_spawn event. The DB stores them. The TUI ignores them. Surfacing the tree relationship makes monitor + shell telemetry interpretable ("this Bash failure happened inside an Explore subagent of session oo-7f3a") instead of just a flat event stream.

OptionProsCons
Add parentage column + TUI tree view
DO		 "This session spawned 12 Explore agents and 3 plan agents" becomes a queryable fact. Cost attribution improves — aggregate sub-agent token spend per parent. TTS announcements can suppress sub-agent noise ("session done" means the parent, not its 12 children). Schema migration on sessions: add parent_session_id, child_role columns + index. TUI work to render the tree.
verdict
Cheap, high-leverage. The data is already arriving on every agent_spawn; we're just throwing it away. Add the columns, backfill from session_events.metadata, then teach the TUI to indent children under parents.
08.6 · collapse notifier + tts-player into a Swift menu bar app

Two launchd processes + a FIFO → one signed app.

Today: com.nexus.notifier (bash, SSE subscriber) + tts-queue.fifo + com.nexus.tts-player (bash, FIFO drain). Three moving parts on the Mac side, each installed via launchd plist, debuggable only via tail-log. A Swift menu bar app could host all three.

OptionProsCons
Keep bash + FIFO (today)
MAYBE		 Zero compile step. Editable with any text editor. terminal-notifier + afplay + say ship with macOS. Two launchd processes to keep alive. FIFO IPC is hard to debug — lost messages disappear. No UI, only logs. Cancel-on-click feature requires PID-file IPC dance.
Swift menu bar app
DO		 One process. Native menu bar icon with state. UNNotificationCenter for click actions (no PID-file dance). AVAudioPlayer for serial playback with native interruption. Settings UI live in the menu. Properly signed & notarized for distribution. Compile step. Requires Apple developer setup for signing. Adds Swift to the project's language footprint. Migration: ship both, deprecate bash over a release.
verdict
Do it. The current bash stack is an MVP that's earned its replacement. A Swift app gets us a real cancel-on-click, real settings UI, a menu bar icon that reflects connection state, and one process instead of three. The migration path is clean — ship both, default to Swift on fresh installs, deprecate bash after a release cycle.
08.7 · full-width 2-col with sticky sidebar diagram (this page)

The pattern you just asked for, evaluated honestly.

A persistent sidebar diagram that highlights the region under discussion as the reader scrolls is the format you requested. Worth noting what it costs.

OptionProsCons
2-col + sticky sidebar (now)
DO		 Reader never loses spatial context. Cross-references resolve visually instead of by name. Hover bridges section ↔ system region. Scanning a long document with persistent reference is faster than scrolling between diagrams. Sidebar collapses below 1280px — mobile loses it entirely. summary
Five DO, two MAYBE, three SKIP. The DOs cluster around "information already exists, surface it" (sub-agent tree, sequential emit, 60m idle, global hooks). The MAYBEs are durability investments (configurable timeouts, persist-then-emit-with-payload). The SKIPs are premature unifications that would lose real properties — HTTP-only or socket-only ingestion both fail the smell test for the same reason: they discard an asymmetry that exists for a reason.
A Cartography of Telemetry — end.

Seven plates, three protocols, two processes, one bus. The shape of Nexus is governed by a single insistence: no machine should depend on a machine that isn't on the user's Tailnet. Everything that follows from that — peer federation, network-layer auth, the write-through cache, the FIFO between listener and player — is a consequence, not a choice.
